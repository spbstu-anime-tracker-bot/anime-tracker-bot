# Anime Tracker and Advisor Bot — Architecture

# 1. Требования к технологическому стеку

* **Telegram API**: приложение должно быть интегрировано с Telegram API для реализации пользовательского интерфейса в формате Telegram-бота.
* **LLM API**: приложение должно быть интегрировано с Gemini API для генерации персонализированных рекомендаций по аниме.
* **Язык программирования**: Java 25.
* **Фреймворк**: Spring 7.
* **База данных**: PostgreSQL.
* **ORM / доступ к данным**: Spring JPA + Hibernate.
* **Брокер сообщений**: Kafka.
* **Сборка проекта**: Gradle.
* **Контейнеризация**: Docker, Docker Compose.
* **Источник данных**: локальная база данных, сформированная на основе MyAnimeList Dataset.
* **Тестирование**: JUnit.
* **Логирование**: SLF4J.

## 2.1. Сервер

**Роль:** центральный компонент системы.

**Функционал:**

* принимает входящие HTTP-запросы от Telegram-бота;
* принимает административные HTTP-запросы;
* маршрутизирует пользовательские команды в соответствующие модули;
* координирует взаимодействие между модулями, базой данных, Kafka и Gemini API;
* обеспечивает обработку ошибок и возврат корректных сообщений пользователю.
---

## 2.2. Telegram-бот

**Роль:** пользовательский интерфейс системы.

**Функционал:**

* принимает сообщения и команды пользователя через Telegram;
* передает команды на сервер по HTTP;
* отображает пользователю результаты поиска, списки, карточки аниме и рекомендации;
* обрабатывает нажатия на следующие кнопки: добавление в список просмотренных, добавление в список на просмотр, удаление из списков, выставление оценки, переход между страницами, кнопки меню.

---

## 2.3. User

**Роль:** конечный пользователь Telegram-бота.

**Функционал:**

* запускает бота командой `/start`;
* ищет аниме по названию с помощью команды `/search`;
* выполняет расширенный поиск через `/search_by`;
* добавляет аниме в список просмотренных или запланированных;
* удаляет аниме из пользовательских списков;
* выставляет оценку просмотренному аниме;
* просматривает свои списки через `/list_viewed` и `/list_to_view`;
* получает персональные рекомендации через `/advise`.

---

## 2.4. Admin

**Роль:** пользователь, выполняющий административное управление системой.

**Функционал:**

* обращается к административному HTTP API;
* проходит проверку через административный токен;
* получает список зарегистрированных пользователей;
* проверяет состояние системы через healthcheck endpoint.

# 3. Внутренние API сервера

## 3.1. API Telegram messages handlers

**Роль:** входная точка для сообщений Telegram-бота.

**Функционал:**

* принимает HTTP-запросы от Telegram-бота;
* определяет тип команды пользователя;
* передает запрос в соответствующий модуль;
* обрабатывает запросы от кнопок;
* возвращает результат в формате, удобном для отправки пользователю в Telegram.

**Обрабатываемые команды:**

* `/start`;
* `/search <название>`;
* `/search_by <параметры>`;
* `/list_viewed`;
* `/list_to_view`;
* `/advise`;
* неизвестные команды и некорректный ввод.

---

## 3.2. API Healthcheck

**Роль:** проверка работоспособности системы.

**Функционал:**

* принимает HTTP-запросы от пользователя или администратора;
* проверяет доступность сервера;
* проверяет доступность PostgreSQL;
* проверяет доступность Kafka;
* проверяет доступность внешнего Gemini API;
* возвращает статус системы.

---

## 3.3. API Admin Interface

**Роль:** административный интерфейс системы.

**Функционал:**

* принимает административные HTTP-запросы;
* передает запросы в модуль авторизации администратора;
* предоставляет доступ к списку пользователей;
* может использоваться для мониторинга и проверки состояния системы.

# 4. Основные модули системы

## 4.1. AuthUserModule

**Роль:** регистрация и идентификация пользователей.

**Функционал:**

* обрабатывает команду `/start`;
* проверяет наличие пользователя в базе данных по Telegram ID;
* автоматически регистрирует нового пользователя при первом обращении;
* сохраняет Telegram ID и имя пользователя;
* предоставляет другим модулям информацию о пользователе.

---

## 4.2. SearchAnimeModule

**Роль:** поиск аниме в локальной базе данных.

**Функционал:**

* обрабатывает команду `/search <название>`;
* выполняет регистронезависимый поиск по названию;
* обрабатывает команду `/search_by <параметры>`;
* фильтрует аниме по жанру, типу и году выхода;
* проверяет корректность введенных критериев;
* возвращает сообщение об ошибке при нераспознанном критерии;
* сортирует результаты по метрике Popularity.

Метрика сортировки рассчитывается по формуле:

```text
Popularity = Rating * log10(Users)
```

Если результаты поиска отсутствуют, модуль возвращает сообщение:

**«Аниме не найдены»**.

---

## 4.3. DisplayCardsModule

**Роль:** формирование карточек аниме для отображения в Telegram.

**Функционал:**

* получает список найденных аниме или рекомендаций;
* разбивает результаты на страницы по 5 карточек;
* формирует отдельное сообщение для каждой карточки;
* добавляет интерактивные кнопки;
* формирует кнопки навигации «Предыдущая» и «Следующая».

**Состав карточки:**

* название;
* описание;
* рейтинг;
* жанры;
* тип;
* статус;
* количество эпизодов;
* дата выхода.

**Интерактивные кнопки:**

* «Добавить в просмотренные»;
* «Удалить из просмотренных»;
* «Добавить в отслеживаемые»;
* «Удалить из отслеживаемых»;
* «Поставить оценку».

---

## 4.4. ManageUserListsModule

**Роль:** управление пользовательскими списками.

**Функционал:**

* добавляет аниме в список просмотренных;
* удаляет аниме из списка просмотренных;
* добавляет аниме в список запланированных к просмотру;
* удаляет аниме из списка запланированных;
* проверяет, не находится ли аниме уже в выбранном списке;
* сохраняет изменения в PostgreSQL;
* передает обновленные данные в модуль отображения карточек.

---

## 4.5. DisplayUserListsModule

**Роль:** отображение пользовательских списков.

**Функционал:**

* обрабатывает команду `/list_viewed`;
* обрабатывает команду `/list_to_view`;
* получает из базы данных список просмотренных или запланированных аниме;
* передает данные в DisplayCardsModule;
* возвращает пользователю список в формате карточек.

Если список пуст, пользователь получает соответствующее сообщение.

---

## 4.6. RateAnimeModule

**Роль:** выставление и обновление оценок пользователя.

**Функционал:**

* обрабатывает нажатие кнопки «Поставить оценку»;
* предоставляет пользователю выбор оценки от 1 до 10;
* сохраняет оценку в базе данных;
* обновляет уже существующую оценку, если пользователь изменил свое мнение;
* помечает рекомендации пользователя как устаревшие.

Если пользователь добавил новую оценку, старый кэш рекомендаций больше не считается актуальным.

---

## 4.7. AdviseModule

**Роль:** обработка пользовательского запроса на получение рекомендаций.

**Функционал:**

* обрабатывает команду `/advise`;
* проверяет, есть ли у пользователя актуальный кэш рекомендаций;
* если кэш актуален — возвращает сохраненные рекомендации;
* если кэш устарел — создает запрос на генерацию новых рекомендаций;
* отправляет событие в Kafka;
* сообщает пользователю, что рекомендации формируются;
* после завершения обработки получает результат и передает его в DisplayCardsModule.

Для пользователя процесс должен выглядеть так: он отправляет `/advise`, бот сообщает, что рекомендации готовятся, а затем присылает результат после завершения фоновой обработки.

---

## 4.8. RecommendationWorker

**Роль:** фоновая обработка запросов на рекомендации.

**Функционал:**

* читает события из Kafka;
* получает из PostgreSQL оценки пользователя;
* формирует промпт для Gemini;
* отправляет запрос к Gemini API;
* получает список рекомендованных аниме;
* сопоставляет рекомендации LLM с локальной базой данных;
* сортирует итоговый список по Popularity;
* сохраняет рекомендации в PostgreSQL;
* обновляет статус запроса;
* отправляет событие о завершении обработки.

RecommendationWorker нужен для того, чтобы длительные запросы к LLM не блокировали основной поток обработки Telegram-команд.

---

# 5. Внешние API и инфраструктурные компоненты

## 5.1. API Gemini 

**Роль:** внешний сервис генерации персональных рекомендаций.

**Функционал:**

* принимает запрос от RecommendationWorker;
* анализирует оценки пользователя;
* формирует список из 10 рекомендованных аниме;
* возвращает результат в структурированном формате.

В запрос к Gemini передаются не все данные пользователя, а только необходимые для рекомендации сведения: названия просмотренных аниме, оценки, жанры и предпочтения, которые можно вывести из истории пользователя.

Если Gemini не отвечает в течение 1 минуты, система возвращает сообщение:

**«Функция временно недоступна. Попробуйте повторить запрос через некоторое время»**.

---

## 5.2. API Kafka

**Роль:** асинхронная обработка запросов на рекомендации.

**Функционал:**

* принимает события о необходимости сформировать рекомендации;
* передает события RecommendationWorker;
* хранит сообщения до момента обработки;
* позволяет повторно обработать запрос при временной ошибке;
* отделяет основной Telegram API от долгой операции обращения к LLM.

Структура в kafka выглядит следующим образом:

```text
recommendation.requests
recommendation.results
```

В `recommendation.requests` отправляется событие о создании запроса.

В `recommendation.results` отправляется событие о завершении обработки.

Пример события запроса:

```json
{
  "requestId": "uuid",
  "telegramId": 123456789,
  "createdAt": "2026-05-17T12:00:00",
  "type": "GENERATE_RECOMMENDATIONS"
}
```

Пример события результата:

```json
{
  "requestId": "uuid",
  "telegramId": 123456789,
  "status": "COMPLETED"
}
```

Такой подход надежнее, чем передача только токена запроса, потому что по `requestId` можно восстановить состояние операции, найти пользователя, проверить статус и обработать ошибку.

---

## 5.3. API Spring JPA + Hibernate

**Роль:** слой доступа к данным.

**Функционал:**

* выполняет запросы к PostgreSQL;
* сохраняет пользователей;
* получает данные об аниме;
* сохраняет пользовательские списки;
* сохраняет оценки;
* сохраняет кэш рекомендаций;
* сохраняет статус запросов на рекомендации.

Этот слой изолирует бизнес-логику от прямой работы с SQL и обеспечивает единый способ доступа к данным.

---

## 5.4. PostgreSQL

**Роль:** основное хранилище данных системы.

**Функционал:**

* хранение пользователей;
* хранение данных об аниме из MyAnimeList Dataset;
* хранение пользовательского списка просмотренных аниме;
* хранение пользовательского списка запланированных аниме;
* хранение пользовательских оценок аниме;
* хранение жанров аниме;
* хранение кэша рекомендаций;
* хранение статусов запросов на рекомендации.

В базе данных должны присутствовать сущности:

* `user` — хранение информации о пользователях Telegram;
* `anime` — хранение информации об аниме из MyAnimeList Dataset;
* `genre` — хранение списка жанров;
* `animeGenres` — таблица связи many-to-many между аниме и жанрами;
* `listViewed` — список просмотренных аниме пользователя и пользовательские оценки;
* `listToView` — список аниме, запланированных к просмотру.
* `recommendation_requests` — хранение статусов запросов на рекомендации;
* `recommendation_cache` — хранение закэшированных рекомендаций пользователей.

# 6. Логика работы рекомендаций

## 6.1. Получение рекомендаций из кэша

Если пользователь отправляет команду `/advise`, система сначала проверяет актуальность сохраненных рекомендаций.

Кэш считается актуальным, если после последней генерации пользователь не добавлял новые оценки и не изменял старые.

**Последовательность действий:**

1. Пользователь отправляет `/advise`.
2. AdviseModule проверяет наличие актуального кэша.
3. Если кэш найден, рекомендации сразу передаются в DisplayCardsModule.
4. Пользователь получает список рекомендаций в виде карточек.

---

## 6.2. Генерация новых рекомендаций

Если кэш отсутствует или устарел, запускается асинхронная обработка.

**Последовательность действий:**

1. Пользователь отправляет `/advise`.
2. AdviseModule создает запись в `recommendation_requests`.
3. В Kafka отправляется событие в тему `recommendation.requests`.
4. RecommendationWorker получает событие.
5. RecommendationWorker запрашивает оценки пользователя из PostgreSQL.
6. RecommendationWorker формирует запрос к Gemini.
7. Gemini возвращает список рекомендаций.
8. RecommendationWorker сопоставляет названия с локальной базой аниме.
9. RecommendationWorker сохраняет результат в `recommendation_cache`.
10. RecommendationWorker отправляет событие в `recommendation.results`.
11. Пользователь получает готовые рекомендации.

---

# 7. Модуль HealthCheck

## 7.1. HealthCheckModule

**Роль:** системный мониторинг.

**Функционал:**

* проверяет доступность основного сервера;
* проверяет подключение к PostgreSQL;
* проверяет подключение к Kafka;
* проверяет доступность Gemini API;
* возвращает общий статус системы.

Пример ответа:

```json
{
  "status": "UP",
  "postgresql": "UP",
  "kafka": "UP",
  "gemini": "UP"
}
```

Если один из компонентов недоступен, статус системы должен отображать частичную ошибку, например:

```json
{
  "status": "DEGRADED",
  "postgresql": "UP",
  "kafka": "UP",
  "gemini": "DOWN"
}
```

# 8. Модуль администрирования

## 8.1. AuthAdminModule

**Роль:** авторизация администратора.

**Функционал:**

* проверяет HTTP-заголовок `Authorization`;
* сверяет Bearer-токен с токеном из переменных окружения;
* запрещает доступ при неверном или отсутствующем токене.

Пример заголовка:

```text
Authorization: Bearer <ADMIN_API_TOKEN>
```

---

## 8.2. ListUsersModule

**Роль:** получение списка зарегистрированных пользователей.

**Функционал:**

* принимает запрос от API Admin Interface;
* проверяет авторизацию администратора;
* получает список пользователей из PostgreSQL;
* возвращает Telegram ID, дату регистрации и базовую статистику пользователя.

Базовой статистикой пользователя является:

* Telegram ID;
* количество просмотренных аниме;
* количество аниме в списке запланированных;
* количество выставленных оценок.

---

# 9. Обработка ошибок

## 9.1. Ошибки пользовательского ввода

**Ситуация:** пользователь вводит неизвестную команду.

**Ответ:** сообщение о том, что команда не распознана.

**Ситуация:** пользователь вводит некорректный критерий в `/search_by`.

**Ответ:**

```text
Введён несуществующий критерий — '{Значение}'
```

**Ситуация:** поиск не дал результатов.

**Ответ:**

```text
Аниме не найдены
```

---

## 9.2. Ошибки LLM

**Ситуация:** Gemini не отвечает в течение 1 минуты.

**Ответ:**

```text
Функция временно недоступна. Попробуйте повторить запрос через некоторое время
```

При этом запрос помечается в базе данных соответствующим образом.

---

## 9.3. Ошибки Kafka

Если Kafka временно недоступна, система не должна терять запрос пользователя. Поэтому сначала создается запись в `recommendation_requests` со статусом `CREATED`. Затем производится попытка отправить событие в Kafka. Если отправка не удалась, пометить запрос как `FAILED_TO_SEND`и пользователю возвращается сообщение о временной недоступности функции.
